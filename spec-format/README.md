# Spec Format Standard

The spec is **one materialized whole-corpus document, stored as many tiny content-only fragments.**
Authors edit fragments; a build assembles the navigable HTML index. This page is the standard: how to
shard, name, anchor, ID, cross-ref, and compile.

Mirrors Mistwright's `.body.html` pattern. Load it at **Stage 3 (spec-first)** and when wiring
`link_check`. Project values (shard root, `clauseIdRegex`, build command, authoring format) live in
`project-details.md#SPEC-1`. Scripts ship as twins: `.ps1` on Windows, `.sh` on Linux/macOS.

---

## 1. The non-negotiable rule: CONTENT-ONLY shards

Every spec subsection is its own fragment containing **markup and EARS clauses ONLY**:

- **No** `<!doctype>`, `<html>`, `<head>`, `<body>`.
- **No** `<style>`, `<script>`, inline CSS, nav/header/footer chrome.
- **Yes** headings, lists, tables, code blocks, anchors, cross-ref links — paragraphs only where a rule
  cannot be a line (§5).

All page chrome (CSS, scripts, nav, the HTML skeleton) lives in **exactly one** `spec/_layout.html`,
never repeated in a fragment. Load-bearing, not cosmetic — see §7.

---

## 2. Authoring format: Markdown → compile (default)

**Author shards as `*.body.md`; the build compiles them into one `spec/index.html`.**
- Markdown keeps fragments diff-friendly and agent-cheap; the build still yields the human whole-corpus HTML.
- Raw-HTML authoring (`*.body.html`, Mistwright-style) is **permitted by config** (`project-details.md#SPEC-1`);
  Markdown is the shipped default.

| Choose Markdown (`*.body.md`) when | Choose raw HTML (`*.body.html`) when |
|---|---|
| New project, default. Diff-friendly, agent-cheap. | Migrating an existing HTML-fragment corpus (e.g. Mistwright). |
| Authors live in Markdown anyway. | You need exact control of inline anchor markup per clause. |

- Pick one per project, record it in `project-details.md#SPEC-1`, do not mix within a corpus.
- Shard granularity and the content-only rule are **identical** in both.

## 3. Naming & layout

```
spec/
  _layout.html                       # single home of chrome/CSS/JS (build input, NOT a shard)
  <section>/<subsection>.body.md     # content-only fragment (authored)
  <section>/<subsection>.structure.body.md   # the area's type surface: member-level mermaid classDiagram
  index.html                         # COMPILED whole-corpus view — never hand-edit
  archive/                           # folded-out transient working specs (git mv, never delete)
```

- **Path = `spec/<section>/<subsection>.body.md`**, e.g. `spec/5_economy/5b.5_timer.body.md`.
- **Slug** (filename minus `.body.md`) must be stable and unique; the build emits it as the shard's
  `<section id="…">`, so cross-shard hrefs can target it. Renaming a slug is a Patch.
- **Ordering:** shards assemble in lexical path order; prefix an ordering key where sequence matters
  (`0_intro.body.md`, `1_…`). Reordering never renumbers clause IDs (§4).
- **Compiled twin** (`index.html`) is generated by `spec-format/build.*`. Hand-editing it is a
  build-output bug — lost on next fold.
- **Transient working specs** live under the working area named in `project-details.md#SPEC-1`; on DONE
  they fold into the canonical shard and `git mv` to `archive/` (never deleted, never read to
  implement from).
- **Structure shards** (`*.structure.body.md`, `#SPEC-8`) hold the member-level class diagram — every
  class with its public properties and methods — as a fenced `mermaid` `classDiagram`: **text is the
  source, the drawing derives** (add mermaid.js to `_layout.html` to render it).
  - A transient `<ITEM-ID>.structure.body.md` is a **delta** under `## Added` / `## Changed` / `## Removed`
    (`stages/1_design.md`); the canonical one is the area's current state, folded at Stage 7 and read
    first by the next unit's design pass.
  - PM-approved with the spec, frozen with the tests, checked by `structure_check` (`gates/README.md`).
  - The build plan (`<ITEM-ID>.buildplan.md`, `#SPEC-9`) sits beside the transient spec and is
    archived, never folded.

## 4. Anchors & clause IDs (the stable join keys)

Two anchor levels, both stable for the life of the spec:

1. **Section anchor** — derived from the subsection number: `§5b.5`. Emitted as the shard's
   `<section id>` (the slug) and on the lead heading.
2. **Clause ID** — every behavioural clause carries a stable ID derived from the section (`5b.5.2`),
   anchored inline on its element (`id="5b.5.2"` in HTML; `{#5b.5.2}` or an explicit `<a id>` in
   Markdown per your renderer).

- **Clause IDs never renumber.** New clauses **append** the next free number; a withdrawn clause is
  retired by lifecycle tag, never reused — the traceability chain (§7c) stays intact across years.
- **Retire a clause with a one-line lifecycle tag at its anchor, body removed** — never silent-delete,
  never a struck-through stratum (`lifecycle-states.md`).
- Changed text is **replaced wholesale** (`stages/3_spec.md` §"One update method"); the provenance pin
  is the only in-text annotation.
- **`clauseIdRegex`** is defined **once** in `project-details.md#SPEC-1` and mirrored into
  `gates/gates.config.json`, so spec, test plan, and gates agree on what a clause-ID *is*. Default:
  `\b[A-Z]{2,}\.\d+\b` (matches `CB.07`-style); override per project to also match `5b.5.2`-style.

**Lead-comment header (1 line, top of every shard)** declares title/anchor for the build's TOC:

```
<!-- §5b.5 Foundry Timers -->
```

**Provenance pin (Stage 7 fold):** a folded clause gets `(§X per <unit-id>, YYYY-MM-DD)` appended —
`<unit-id>` is a Jira key (Mode A) or backlog id (Mode B), same syntax either way.

## 5. EARS grammar (every behavioural clause)

Each clause is **atomic, testable, and stably-ID'd**, in one of the five EARS forms:

| Form | Template | Use for |
|---|---|---|
| Ubiquitous | `The system shall …` | always-true invariants |
| Event | `When <trigger> the system shall …` | trigger → response |
| State | `While <state> the system shall …` | behaviour bounded by a mode |
| Unwanted | `If <cond> then the system shall …` | error/guard handling |
| Optional | `Where <feature> the system shall …` | feature-gated behaviour |

One clause = one ID = one row in the trace. If a clause needs "and also…", split it.

**Form (per SDD-PROP-09):**
- The shard carries **decisions only** — no rationale, alternatives, or history.
- Structured, not narrative: list items, table rows, code lines; one fact per line; name the concrete
  construct (class, signature, config key, constant).
- Write EARS in its shortest form — `When <trigger>: <response>.` — `the system shall` is optional where
  the subject is obvious.
- A paragraph only where a rule cannot be a line.
- The Stage-7 fold keeps this form verbatim. Exemplars: `project-details.md#SPEC-7`.

### Minimal shard skeleton (`spec/5_economy/5b.5_timer.body.md`)

```markdown
<!-- §5b.5 Foundry Timers -->

# §5b.5 Foundry Timers {#5b.5}

The foundry converts ore to ingots on a fixed timer.

- **5b.5.1** — The system shall display remaining foundry time in whole seconds. {#5b.5.1}
- **5b.5.2** — When the foundry timer reaches zero the system shall move ingots to
  the player inventory. {#5b.5.2}
- **5b.5.3** — If the inventory is full then the system shall pause the timer and
  surface a "storage full" notice. {#5b.5.3}

See also [§5g.4 Storage caps](5_economy/5g.4_storage_caps.body.md#5g.4).
```

## 6. Build step

The build (`spec-format/build.*`) reads **one `_layout.html`**, inlines every fragment in manifest
order under `<section id="…">`, generates a TOC + clause-ID index, and writes `spec/index.html`.

- **Layout contract:** `_layout.html` contains two markers the build replaces — `<!--TOC-->`
  (generated TOC) and `<!--BODY-->` (concatenated shards). Absent, the build emits a minimal default
  so a fresh project still compiles.
- **Recompile on every fold (Stage 7)** so the whole-corpus view never goes stale. CI/the orchestrator
  runs the build; nobody hand-edits `index.html`.
- Command/flags are recorded in `project-details.md#SPEC-1` and surfaced to gates via `gates.config.json`
  (`paths.spec` glob).

```bash
# Windows:
pwsh spec-format/build.ps1 spec   # -> spec/index.html ; prints PASS/FAIL
# Linux/macOS:
sh   spec-format/build.sh  spec   # -> spec/index.html ; prints PASS/FAIL
```

- The shipped build is **PowerShell (native) / Bash (POSIX + awk), both with a built-in Markdown shim**.
- It compiles `*.body.md` via the shim (headings with `{#id}` anchors, fenced code, paragraphs, inline
  markup; raw-HTML lines pass through) and inlines `*.body.html` shards as-is — recursively, both
  extensions, no per-project edit.
- The **content-only** rule holds either way.

## 7. One sharding scheme, FOUR masters

- The fragment boundary is the **smallest independently-meaningful unit** *and* the **natural unit one
  work-item loads**, so loading-, review-, and trace-granularity coincide — and the **content-only
  rule** (§1) makes all four hold at once.
- Any other granularity, or chrome leaking into a shard, loses at least one master.

**(a) Token-efficient staged loading.**
- An agent loads **one** content-only `.body.md` (a few hundred tokens, no layout tokens) — never
  `index.html`, never the whole spec.
- Stage 3 emits a **shard manifest** (clause-ID ranges → shard paths) into the transient working spec;
  Stages 4–7 and every persona dispatch resolve shards from it by path-glob over the work-item's
  clause-IDs. Sub-agents receive only their named shard paths.

**(b) Human navigation.** The build compiles every fragment into one current, styled `index.html` with a
TOC: humans read the **whole**, agents the **part**, from the **same source**; the fold-time recompile
keeps the whole honest.

**(c) Traceability anchors.**
- Section anchor + per-clause ID are the stable join keys for the full chain:
  `clause-ID → numbered scenario → test-ID → code → ship-SHA`.
- The provenance pin `(§X per <unit-id>, YYYY-MM-DD)` attaches at **clause granularity**, so the spec
  stays back-derivable from the changelog.

**(d) Link-checkability.**
- Every cross-ref is an href to a **declared** anchor or clause-ID, so `link_check` is a pure set
  operation: declared anchors ∪ clause-IDs across all shards ⊇ every internal href fragment
  (http/mailto skipped).
- Content-only shards keep the parse trivial and the anchor set unambiguous.

## 8. How shards align to stages and gates

| Touchpoint | Alignment |
|---|---|
| **Stage 3 (spec-first)** | Author/edit shards; emit the shard manifest; PM approves spec **+ the structure shard**; `link_check` + `structure_check --plan` must pass before any test/code. |
| **Stage 4 (test plan)** | `coverage_check --plan`: every clause-ID (via `clauseIdRegex`) maps to ≥1 scenario. The shard is the unit you enumerate clauses from. |
| **Stage 4b (build plan)** | Structure-shard classes → files → slices; the read ledger (`<ITEM-ID>.buildplan.md`) names what each slice reads — ranges, anchors, pins, skips. |
| **Stage 5 (QA)** | QA gets **named shard paths only** (no router, no impl). Tests tag `@clause:<id>` straight from the shard. Freeze covers the structure shard too. |
| **Stage 6 (Engineer)** | Same shards + frozen tests + the frozen structure shard; the shard is the spec of record on disagreement; `structure_check --frozen` proves the diagram did not move. |
| **Stage 7 (ship & fold)** | Fold transient decisions into canonical shards and the structure delta into the canonical structure shard; pin provenance per clause (per class in the diagram); `git mv` working spec + build plan to `archive/`; **recompile `index.html`**; `link_check` + `coverage_check` + `structure_check` re-run in `run_all`. |

**Gate hooks (read these, then the gate scripts):**
- `link_check` (`gates/link_check.*`) — declared-anchor set ⊇ every internal href fragment, across
  `paths.spec`.
- `coverage_check` (`gates/coverage_check.*`) — clause-IDs scraped from `paths.spec` via
  `clauseIdRegex`; assert `clauses ⊆ tested` (and flag `@clause:` tags for unknown clauses).
  - **Whole-corpus at ship:** *every* clause in `paths.spec` needs a test. For **brownfield/incremental**
    adoption, scope `paths.spec` to the SDD-authored shards so the guarantee covers new work only.
  - A `--manifest`/`-Manifest` per-unit mode serves fast in-loop runs; the ship check stays whole-corpus.
- Both read `paths.spec`, `clauseIdRegex`, and `testClauseTag` from `gates/gates.config.json`, which
  mirror `project-details.md#SPEC-1`. Keeping the three in sync is the whole contract.

## 9. Checklist before you commit a shard

- [ ] Content-only: no doctype/html/head/body/style/script/nav.
- [ ] Lead `<!-- §X … -->` header present; slug stable and unique.
- [ ] Every behavioural clause is EARS-form, atomic, and carries a stable inline ID.
- [ ] New clauses appended (no renumbering); withdrawn clauses lifecycle-tagged, never reused; changed text
  replaced wholesale — no struck/bracketed/dated strata.
- [ ] Decision-only, structured, one fact per line; no rationale, history, or framing prose.
- [ ] Every cross-ref href targets a declared anchor/clause-ID (`link_check` will enforce).
- [ ] `clauseIdRegex` in `project-details.md#SPEC-1` matches your IDs and `gates.config.json`.
- [ ] Ran the build (`spec-format/build.*`); `index.html` regenerated, never hand-edited.
